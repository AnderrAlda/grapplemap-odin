# 0002. Oracle: the original built in Docker as the source of truth
Status: Proposed
Date: 2026-11-21

## Context
The goal is exact fidelity to the original GrappleMap: the same body, the same data and the same computed results
(`CLAUDE.md`, `docs/specs/phase-1-original-research.md`). The original is a 2020 C++ code base
(`reference/GrappleMap`, `-std=c++1y`, SCons, Boost, OSMesa). Reading its code is enough to describe it
(`docs/original.md`), but not to prove that a port matches it: floating-point order of operations, parser corner
cases and node matching are easy to get subtly wrong. We need something that runs the original's own code and
records what it produces, on any machine (macOS laptops, Linux CI).

## Decision
1. **Pinned source.** `reference/GrappleMap` is a read-only submodule pinned at `032c8f9`
   (`reference/CLAUDE.md`). It is **never patched**: the image builds a copy, out of tree, with the original
   `SConstruct` flags unchanged (`-std=c++1y -DNDEBUG -O3 -DUSE_FTGL`, `reference/GrappleMap/src/SConstruct:4`).
   If a patch ever becomes unavoidable it goes in `tools/oracle/patches/` and this ADR is amended first.
2. **Pinned toolchain.** `tools/oracle/Dockerfile`, `linux/amd64` only: `ubuntu:18.04` pinned by digest, every
   package at an exact version (GCC 7.5.0, glibc 2.27, Boost 1.65.1, Mesa 20.0.8), generic `-march=x86-64`
   enforced by a build guard (`tools/oracle/Dockerfile:32-33`), no `-ffast-math`, no `apt-get upgrade`. Bionic is
   the newest base whose Boost still ships the legacy GIL IO the original needs (`tools/oracle/README.md`, "Why
   Ubuntu 18.04").
3. **Dumper linked to the original.** `tools/oracle/dump/dump.cpp` links the original's `common` objects
   (`reference/GrappleMap/src/SConstruct:33`), so every dumped value is computed by the original's code, not by a
   re-implementation. Its own arithmetic is built with `-ffp-contract=off` (`tools/oracle/Dockerfile:50-54`).
4. **Dump format.** NDJSON, fixed order, no timestamps. Inputs read from `GrappleMap.txt` are stored quantized
   (the integer base62 value, `0…3843`), computed results as doubles with `%.17g` (exact round-trip). Files and
   fields: `tools/oracle/README.md`, "Dumper".
5. **Sample in git, full dump in CI.** Only a hand-picked sample (normal cases plus every anomaly class, hard limit
   2 MB) is committed in `tests/fixtures/oracle/` with its `MANIFEST.sha256` (#35). The full dump (~0.54 GB,
   `tools/oracle/README.md`) is generated by a separate `oracle` workflow (#36) and checked against the committed
   `FULL.sha256`; from phase 2 the Odin fidelity tests run over it in CI. `./build.sh ci` and `./build.sh test`
   never need Docker: locally they use the sample. If the full dump does not fit the CI artifact limits or the job
   time, it is split by file; the Odin comparison is never moved to a subset without Ander's OK (spec, "Edge cases").
6. **Direction of truth.** The Odin code is verified against the oracle, never the other way round. Fixtures are
   regenerated only by `./build.sh oracle`, and a change to them goes in the PR that changes the dumper or the pin, with
   the reason.
7. **Timebox.** If the original stops building in the image (a base image move, a pin bump), oracle work stops and
   Ander is asked before patches or another approach are tried (spec, "Order and priority").

## Alternatives
- **Port by reading the code only.** No dependency on Docker, but no evidence of fidelity: every subtle
  difference (operation order, parser corner cases, matching order) would surface only by eye, if ever.
- **Run the original's web JS** (`reference/GrappleMap/src/*.js`, fed by `grapplemap-dbtojs`). Easier to run, but
  it is a second implementation (and an emscripten build with its own flags, `src/SConstruct:16`), not the C++
  code the data and images come from, and it does not expose parsing or node matching.
- **Patch the original** (modern Boost, a dump mode inside its tools). Simpler builds, but the oracle would no
  longer be the original, and every patch is a place where it can diverge.
- **Commit the full dump.** Self-contained tests, but ~0.54 GB of churn in git for every dumper change.
- **Build natively on each developer machine.** No Docker, but on arm64 (Apple Silicon) GCC and clang contract
  multiply-adds into FMA by default, and libm/Boost versions vary: outputs would differ between machines (ADR 0003).

## Consequences
- Docker is needed to regenerate fixtures or run the oracle (`./build.sh oracle`), not to build or test the
  port. On Apple Silicon the image runs emulated and slowly.
- Drift is caught, not prevented: a different compiler, libm, Boost or Mesa that changes any output changes a
  hash in `MANIFEST.sha256`/`FULL.sha256` and fails the `oracle` workflow. Bionic's archive may move to
  `old-releases`; the digest and exact versions make that fail loudly rather than silently change.
- Rendered PNGs depend on the Mesa version: they are regenerated by hand (`--images`, #35), hashed, and not
  compared pixel by pixel in CI. They are rendered with Mesa's **softpipe** driver (`GALLIUM_DRIVER=softpipe`):
  the image's default llvmpipe corrupts the original's `OSMESA_RGB` buffer and its bytes vary per run and per host
  (`tools/oracle/README.md`, "Reference images").
- Bumping the pin invalidates the sample, `FULL.sha256` and the inventory (`docs/original.md` §10): it needs its
  own PR that regenerates all three.
- Local fidelity tests only cover the sample; full coverage depends on the CI artifact.
